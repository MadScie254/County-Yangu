# Working in this repository

County Yangu (residents) and CountyConnect (county staff) are one system: two doors, one database, one Supabase project per county.

- `src/resident` is the public app (served at `/`); `src/console` is the staff app (served at `/console`). They are separate bundles built from one Vite project. `src/shared` is used by both.
- The database is the source of truth for every rule: `supabase/migrations`. Public writes go through `supabase/functions` (Deno), which call `svc_*` database functions. Read `supabase/functions/README.md` before changing either.
- Never put a secret in a `VITE_` variable: those ship to every browser. Secrets live in `supabase/.env` (gitignored) and Supabase function secrets.
- A role is only ever a row in `staff_roles`. Never derive permissions from user metadata, the URL, or a form choice.
- One account, two spaces: `/me` is the citizen dashboard, `/console` the staff console. Anyone signed in reaches `/me`; the staff switch only appears for people with a `staff_roles` row.
- Transparency rules (who wins tenders, red flags) live in the database (`procurement_watch`, migration 0012). `src/shared/lib/procurement.ts` is its demo-mode twin: change both together, and keep `tests/unit/procurement.test.ts` and `tests/db/procurement.test.mjs` in step.
- The resident loop (migrations 0013 to 0015): feedback and reopening (`svc_case_feedback`, Edge Function `case-feedback`), SMS on change (triggers on `report_events` and `applications`, so no code path sends its own), permit codes (`verify_document`, `revoke_document`), ward results and quarterly rounds (`budget_results`, `svc_round_scheduler`), follows (RLS-owned rows, notifications from triggers), committee and ward views, OCDS export. `src/shared/api/loop.ts` is the browser side with a labelled demo fallback; Kiswahili flag wording lives in `loop.flags.*` and `src/shared/lib/flagText.ts`. Tests: `tests/db/resident_loop`, `participation`, `open_data`, `tests/unit/flagText`.
- Migration 0017: "me too" (`svc_case_metoo`, via the `case-feedback` function with `action: 'metoo'`; supporters stored only as keyed hashes; ten voices raise priority) and the public participation calendar (`public_meetings`, notifies ward followers and instant SMS subscribers). Navigation groups for every public page live in `navGroups` in `src/resident/layout/ResidentShell.tsx`; add new pages there so they appear in the Explore menu, the phone menu and the footer together.
- Migration 0018: open reports shown while reporting (`open_cases`, so residents press "me too" instead of filing a duplicate) and community project checks (`svc_project_check` via `case-feedback` with `action: 'project_check'`; one keyed-hash answer per person; the third "not as shown" and every tenth after notify staff; public tally from `project_checks`). `/compare` puts two ward scorecards side by side. Tests: `tests/db/duplicates_checks`.
- Migration 0019: service notices (`service_notices`; ward staff post for their own ward only, county-wide needs a county role; followers are notified and instant SMS subscribers texted for disruptions, emergencies and the all clear) and the promise tracker (`commitments` plus `commitment_updates`, a public history written only by trigger, so status changes and moved due dates cannot be hidden; follow kind `commitment`). Active disruptions show in `NoticesStrip` under the resident header. Tests: `tests/db/notices_commitments`, `tests/unit/promises`.
- Migration 0020, rights residents already have in law: information requests under the Access to Information Act 2016 (`info_requests`; the 21-day, 48-hour and one-time 14-day extension rules live in the `info_requests_rules` trigger; column grants hide `user_id`, own requests via `my_info_requests()`), consultations on drafts (`consultations`, `consultation_comments`, comments only while open, `consultation_tally`, a report notifies everyone who commented), a guaranteed petition answer (200 supporters in a ward, 1,000 county-wide, 30 days; `petitionGoal` in `src/shared/api/rights.ts` is its twin), and Data Protection Act rights (`my_data()`, `request_erasure()`, admin `erasure_queue()` and `carry_out_erasure()`). Browser side: `src/shared/api/rights.ts`. Tests: `tests/db/rights_participation`.
- Supabase advisor hygiene (migration 0016): owner-rights views and API functions live in the unexposed `internal` schema; `public` only has SECURITY INVOKER views and wrappers of the same name. When you add a public RPC that must run with owner rights, write it in `internal` and add a thin invoker wrapper in `public` with the same grants.
- No em dashes or en dashes anywhere, in copy or code.
- Live-first data with a labelled demo fallback: screens must work with no backend (`VITE_FORCE_DEMO=1`).

Checks before you commit: `npx tsc --noEmit`, `npx eslint src`, `npm test`, `npm run test:db`, and (needs Deno) `npm run test:edge` and `npm run check:edge`.
